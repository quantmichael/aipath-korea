# Metadata Candidate atomic publication

This release keeps the existing Full Raw publish queue and Service registration
path. Metadata publication uses the existing explicit Candidate-ID method on
`PublishWorker`. Local Automation assembly now also enables bounded selection
of pending operational Metadata Candidates behind both `publish_enabled` and
`publish_worker_enabled`. Defaults remain OFF; this change has not been deployed.

## Automatic dispatch in the local release

`AutomationRuntime.run_once` acquires the existing global lease and runs the
existing PublishWorker. Full Raw jobs retain priority and reserve their selected
slots, even if another worker wins their claim. Only remaining slots in
`publish_max_jobs_per_run` may process Metadata. A failed Full Raw pass prevents
additional Metadata processing. There is no new Worker, queue, migration or flag.

Selection reads operational PUBLISH_READY Candidates in stable order and excludes
immutable publish completions. Both reads must be complete within the existing
SDK `max_records` ceiling (500 by default); overflow or unavailable counts stop
the pass. Completed history counts toward this ceiling; this is a safety limit,
not unlimited-scale pagination. Full Raw saturation can defer Metadata.

Before fetching, the Runtime requires the existing ACTIVE/collectible Source and
authenticated, non-revoked, current Metadata permission. A Source explicitly
marked `synthetic_only` is held by automatic dispatch. It uses the existing
robots-aware, DNS-pinned transport for exact approved permission/page URLs and
rejects redirects to a different URL before fetching that destination. Permission
hashes must match. The immutable approval snapshot must contain the existing
019 action-rights contract: public_read, automated_access, fact_extract,
fact_store and fact_display are individually ALLOWED with replayable permission
block references. All eight action entries must be structurally valid. The
preserved Minimum Evidence rights parser/replay helper is reused without copying
its unrelated timezone/policy changes. Legacy fact_use alone does not authorize
new publication. Missing rights hold automatic Candidates before page access;
the explicit-ID method also rejects missing rights before the atomic RPC.
Bytes remain transient. No approval, activation, credential,
timezone policy or Evidence is generated by this connection.

The explicit-ID worker then replays Evidence, checks duplicates, records the
assessment, verifies Service mapping and invokes the existing atomic RPC. SQL
remains the final transactional check. A failed permission/page recheck supplies
no Evidence and the existing assessment holds the Candidate. UNKNOWN stops the
rest of this pass without retry; a later scheduled tick selects/rechecks current
state and immutable completions rather than treating UNKNOWN as a failed commit.
No new durable Metadata attempt/lease table is introduced. Worker failures make
Automation PARTIAL (`PUBLISH_INCOMPLETE`), with aggregate Metadata counts and
sanitized outcome codes in the existing log.

Dry run only lists pending IDs with FRESH_EVIDENCE_RECHECK_REQUIRED: no page GET,
assessment write or publish RPC. Manual `publish-worker` and `metadata-publish`
construction do not implicitly opt into automatic selection. The explicit
Candidate-ID method remains available for separately approved canaries.

Offline integration tests execute the real Automation assembly, worker,
extractor/resolver and Service envelope with synthetic HTTP/DB transports. Preview
GET-only selection and unchanged fingerprints are verified separately. Neither is
a claim that this new automatic path has published to a live database.

A separate isolated PostgreSQL 17.10 test now exercises the actual Runtime,
repository mapping and atomic SQL through Agent 018 and, optionally, the exact
reviewed Migration 019 SQL. Five categories plus a full stored-Discovery handoff
produce six local synthetic registrations; repeated dispatch adds none.
Revocation, insufficient rights and injected completion failure are checked.

The optional 019 file must match SHA-256
`30e0db6360d8fc9434932c049c3aeceb089f8ad53262547500319d41834c418f`.
The test creates only a disposable loopback PostgreSQL cluster, accepts no live

Agent and Service tables reside in the same Supabase PostgreSQL project.
Migration 018 adds `agent_publish_metadata_candidate(uuid,jsonb,jsonb)`, granted
only to `service_role`. It locks the Metadata approval and Candidate, checks
the live Source, reviewed permission and revocation audit, the latest fresh
VERIFIED/UNIQUE/PUBLISH_READY assessment audit, a unique approved Service Source mapping and
category, Candidate facts and time provenance. It calls the existing Service
004 `register_opportunity_with_evidence` RPC and writes an immutable Metadata
completion row in the same transaction. A completion insert failure rolls back
the Opportunity and Time Evidence. A preexisting Opportunity is rejected; an
existing completion is returned idempotently. The completion stores the exact
registration envelope, and its Service UUID is historical rather than an FK
so Preview synthetic Service rows can be removed without altering audit rows.

The worker requires a fresh, caller-supplied official page and permission
document. It replays Evidence and re-records assessment before constructing
the Service envelope. SQL checks that the assessment and approval are still
current at DB time. A lost RPC response is reconciled against completion and
Service readback; otherwise the result is UNKNOWN, never success. The DB
cannot replay HTML itself, so the process and its trusted `service_role`
credentials remain the Evidence replay boundary. No external page fetch is
performed by this publish method.

Apply order for a future release is Agent 016, Agent 017, Agent 018, then an
image containing this code. Service 004 is already a prerequisite. Each
migration needs project-specific preflight and approval. Existing images do
not invoke 018, so schema-first deployment is compatible. The migrations are
not automatically reversible because immutable audit records and Service
publication can exist; a rollback should disable both publish flags and
return to the previous image while preserving audit and published records.

The `metadata-publish` CLI requires one `--candidate-id`, `--page-file`,
`--page-url`, `--fetched-at`, `--permission-file`, and
`--permission-checked-at`. `--dry-run` performs reads and replay only;
`--once` also requires both publish flags. It never scans other Candidates.
The caller must provide the transient page bytes and permission document.
Service Publish must be enabled only for a
separately approved operational canary; this release does not turn it on.
Preview synthetic E2E must compare the original Service/Agent row fingerprints,
remove only exact synthetic Service Opportunity and Status Scope IDs, retain
immutable approval/completion audit, and report any remaining synthetic Agent
rows. Production publication is outside this stage.

# PHASE 7.3C — Known Source Collection Scheduling

Current status (2026-10-04): `005_collection_scheduling.sql` was applied **once** to Supabase after security hardening. Live catalog, privileges, A/B atomic claim, lease/recovery, window guards, success reconciliation, one HTTP→RawDocument pass, backoff and final test-Source disable were verified. Historical "unapplied" wording below refers to the pre-validation design stage. PHASE 8 downstream processing is a separate, unapplied 006 boundary.

## Scope and Source policy

Only human-approved `ACTIVE`, `is_active=true` Sources with matching approval snapshot and `collection_allowed=true` are eligible. `CANDIDATE`, `REVIEW`, `APPROVED`, `HOLD`, `REJECTED`, `DISABLED` and inconsistent/legacy ACTIVE records fail closed. Discovery signals do not confer approval. The 004 review RPC is still the only Source lifecycle transition; scheduling does not activate or HOLD a Source.

The fixed `schedule_policy=FIXED` has `interval_minutes` (default 720/12h). Human-reviewed configuration may select 180/3h, 360/6h, 720/12h, 1440/24h or 4320/72h; this phase does not adapt interval with AI. The activation trigger creates/resets an Agent-only schedule row using the approved Source's `collection_interval_minutes` or 720. It does not backfill existing ACTIVE rows or modify any existing Source. Re-activation after formal review resets the schedule. A guard blocks interval changes while APPROVED/ACTIVE. Source's existing last timestamps remain CollectionRunner provenance; schedule timestamps are the scheduling authority.

## Due, claim, lease

`agent_source_schedules.next_collection_at` is `timestamptz`. Production `agent_list_due_sources(limit)` returns at most 100 rows satisfying approved ACTIVE status, collection allowance, `review_needed=false`, due time and no live lease. The caller does not supply time. The Python scheduling repository likewise has no caller-time parameter; only the offline in-memory test implementation injects a clock at construction. `list_due` is advisory, never authorization: `agent_claim_due_source` rechecks under a row lock. A transaction-scoped normalized-domain advisory lock plus live lease count enforces the per-domain cap (default 1) across workers. Claim returns a unique `claim_id`, `window_id`, `claimed_by`, `claimed_at`, `claim_expires_at` (default 30 minutes). A second worker cannot claim the same Source/window. `service_role` can read schedule rows, but mutations are RPC-only; no Service table is touched.

### Schedule privilege boundary

`service_role` has `SELECT` on `agent_source_schedules`, **not** direct `UPDATE` or `DELETE`. PostgreSQL requires `UPDATE` privilege for `SELECT ... FOR SHARE`, even when the statement only reads. The scheduled CollectionRun INSERT and UPDATE trigger functions therefore run as explicitly assigned `postgres` owner with `SECURITY DEFINER`; this lets them lock the schedule row without widening application table privileges. They have fixed `search_path=pg_catalog`, schema-qualified Agent table/function references, no dynamic SQL or user parameters, and their default `PUBLIC`/`service_role` direct `EXECUTE` grants are revoked in the same migration transaction. The triggers are attached by the migration owner. Ordinary application Run INSERT/UPDATE still invokes them, but the application cannot call them as general-purpose privileged functions. The trigger checks reviewed ACTIVE Source state, matching live claim, worker, canonical window and DB-clock lease before accepting a scheduled Run; terminal Run identity/status remains protected. The 004 Source review RPC remains the sole lifecycle transition and is unchanged.

Only the bounded `agent_list_due_sources`, `agent_claim_due_source` and `agent_finish_collection` RPCs receive `service_role` EXECUTE. Their `SECURITY DEFINER` ownership and fixed search paths are separate from the Run trigger boundary. Direct schedule mutation remains prohibited; `agent_collection_completions` is also read-only to `service_role`. These are migration contracts, not a claim of live PostgreSQL enforcement: after 005 is applied in a separate task, catalog grants/owners and service-role INSERT/UPDATE/denial cases must be verified against the actual DB.

**DB server time is authoritative.** Due filtering, claim eligibility, live/expired lease checks, `claimed_at`, `claim_expires_at`, failure recovery and completion scheduling use PostgreSQL `clock_timestamp()`. The claim RPC takes one fresh reading after acquiring the Source row lock; unlike transaction-start `now()`, it reflects time elapsed while waiting for a competing worker. The due RPC takes one reading per call. `p_now` and caller-supplied completion time have been removed from production RPC signatures. Application timestamps are for logs/Run provenance, not schedule authorization. A caller cannot fast-forward due or expire a lease by sending a future timestamp.

The worker is sequential and one-shot. `max_jobs_per_run=5`, `max_concurrent_jobs=1`, `max_concurrent_per_domain=1` default to low load. The concurrency setting is an upper bound; this foundation does not create a parallel crawler. A future worker may add per-domain minimum request spacing without changing the schedule contract. Existing CollectionPlanner and HTTP_HTML/RSS/REST_API generic collectors are reused. The request timeout remains the existing collection config setting.

There is no lease heartbeat. Settings validation therefore requires the lease to exceed the configured HTTP timeout × attempts × redirect envelope. Operators must also allow for DNS/storage/database overhead; a worker exceeding its lease can make a duplicate HTTP request after recovery, even though stale completion cannot overwrite the new schedule.

## Completion and recovery

After success, `last_collection_at` and `last_success_at` are set, `consecutive_failures=0`, and `next_collection_at=Run.finished_at+interval`. After genuine failure, `last_collection_at`, `last_failure_at`, failure count and backoff are recorded. The default backoff is 30m, 2h, 6h, then 24h for further failures. At 4 failures, `review_needed=true` stops automatic collection; it **does not** change Source lifecycle to HOLD. Manual review/re-approval is needed to resume. Both policies are configurable; SQL RPC receives the policy explicitly and validates it.

`agent_finish_collection` verifies Source, claim, window and any explicit terminal Run, then checks the database for a `SUCCEEDED` Run in that exact claim/window **before** considering failure. Success is terminal: even a late exception that calls completion with `p_run_id=NULL` cannot apply backoff, increase failures, update `last_failure_at`, or create a retry window when that successful Run exists. The RPC reconciles success from the persisted Run's `finished_at` and the reviewed Source interval; no HTTP call is needed. `CollectionWorker` uses the RPC's returned terminal outcome for its counters instead of trusting a caught exception as a failed collection. If a completion response is lost after commit, the worker retries the idempotent completion without a Run ID; a local Run/claim validation error does not take this retry path.

An Agent-only `agent_collection_completions` row records one terminal outcome per Source/window/claim, including no-Run failures. Repeating either completion returns that outcome without changing counters or moving `next_collection_at`; an explicit mismatched Run ID is rejected. Scheduled terminal Run status and claim/window identity are immutable. Run creation and success transitions coordinate with the schedule row lock so a completion cannot miss a concurrently committed success. A genuine failure with no successful Run receives one backoff transition. A failed process leaves a lease, not a permanent lock. On a later claim after lease expiry, the RPC performs the same success-first reconciliation before any new collection; a stale RUNNING Run becomes FAILED and backs off. Expiration does **not** permit an immediate HTTP retry. A late old worker can read its recorded completion, but cannot mutate a rotated claim. Recovery is triggered by a later due/claim attempt, not by a daemon.

**Window identity:** the DB derives `window_id` deterministically from `(source_id, next_collection_at UTC epoch microseconds)` using a 128-bit MD5 encoding. MD5 here is an identifier encoding, not an authentication or authorization primitive. An unchanged due instant retains the same ID across reads/claims/crash recovery. A policy-controlled backoff or success interval produces a new due instant and therefore a new window; random UUIDs are not generated to evade the unique index. The claim returns the DB window ID, and `CollectionWorker` passes it unchanged into `CollectionRunner` and the Run's `source_config_snapshot.schedule_window_id`. The scheduled-Run DB CHECK requires a canonical, non-NULL UUID window ID; manual Runs may omit it. A scheduled-Run INSERT trigger additionally requires that Source, window, claim ID and worker ID match a live lease, so a direct INSERT with a different valid UUID cannot evade the window boundary. A partial unique index on `(source_id, schedule_window_id)` for `trigger=scheduled` rejects a second Run in that window. A process may still have made an HTTP request just before a crash; exactly-once HTTP is not guaranteed.

## Worker, dry run and CLI

`CollectionWorker.run_once()` queries a bounded due set, claims each Source, calls the existing `CollectionRunner`, completes the schedule, and exits. `source_config_snapshot` on scheduled Runs carries `trigger=scheduled`, `worker_id`, `claim_id`, `schedule_window_id`; manual runs have no scheduled identifiers. The worker writes an Agent `COLLECTION_WORKER_RUN` summary log with worker ID, started/finished times and due/claimed/success/failure/skipped counts.

`python3 -m agent_collect collection-due [--limit N]` reads due Sources. `python3 -m agent_collect collection-worker --dry-run` reports due Source, method, interval and next time but makes **no** claim, HTTP request, CollectionRun, schedule update or log write. `python3 -m agent_collect collection-worker --once --raw-dir /private/path [--worker-id ID]` executes one bounded pass; it is not a scheduler daemon. The raw directory must be persistent/private as in manual collection. These DB commands require migration 005 to be separately applied.

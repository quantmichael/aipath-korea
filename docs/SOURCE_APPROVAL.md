# PHASE 7.3B — Human Source Review, Approval & Activation

## Scope and deployment status

This phase adds a **manual, audited Agent Source lifecycle**. It does not approve or activate the five benchmark Sources, alter existing Candidate records, call an LLM, or write Service tables. Migration [004_source_review_foundation.sql](../agent_collect/migrations/004_source_review_foundation.sql) was applied once to the AIPATH Supabase project on 2026-10-04 after a final safety audit. Its Agent-only objects and role boundaries were verified against the live PostgreSQL catalog. The five pre-existing Sources remained `HOLD/is_active=false`; no Service table was changed.

## Lifecycle contract

| From | Human decision | To | Guard |
| --- | --- | --- | --- |
| `CANDIDATE/HOLD/REJECTED/DISABLED` | begin review | `REVIEW` | reviewer, reason, timestamp |
| `REVIEW` | change type | `REVIEW` | different `source_type`, reviewer and reason |
| `REVIEW` | approve | `APPROVED` | explicit human `collection_allowed=true` and officiality decision; `official` requires confirmed officiality, or `aggregator` with confidence ≥0.8; collection method required |
| `REVIEW` | reject/hold | `REJECTED/HOLD` | reason recorded; no approval |
| `APPROVED` | activate/hold | `ACTIVE/HOLD` | activation requires the exact approval snapshot |
| `ACTIVE` | hold/disable | `HOLD/DISABLED` | collection stops; approval snapshot cleared |

`APPROVED` is inactive. Only `ACTIVE/is_active=true` with a matching approval snapshot is collectible. The snapshot binds canonical URL, normalized domain, source type/trust, confidence, collection method/config, explicit officiality and collection-permission decisions, reviewer and review timestamp. Review, approval and activation are distinct human decisions. Discovery's configured-domain/officiality hints remain `discovery_officiality_signals` in provenance with `discovery_signal_is_approval=false`; they never create approval. An operator must independently check site ownership, collection permission/terms, trust and the proposed configuration. The current API accepts a reviewer identifier but does not authenticate a human itself; callers must provide an authenticated operator identity and protect the service-role credential.

`SourceApprovalService` exposes `begin_review`, `change_source_type`, `approve`, `activate`, `hold`, `reject`, `disable`. Each requires `reviewer` and `reason`; `approve` additionally requires explicit `officiality_confirmed` and `collection_allowed`. Each can receive a `decision_id` for idempotent retries. The in-memory repository serializes transitions. Supabase uses one `agent_review_source` PostgreSQL RPC transaction: lock Source, validate expected state and decision ID, change Agent Source, append one immutable audit event. Two approvals with distinct IDs cannot both move `REVIEW → APPROVED`; a retry with the same ID and same decision is read-only. The event stores source ID, canonical URL/domain, type before/after, from/to review status, reviewer, reason, reviewed_at, approval/activation and officiality/collection-permission decisions, plus captured Discovery signals.

## Migration 004 security boundary (applied)

`service_role` can write Agent Source rows and bypasses RLS, so RLS alone is not a lifecycle boundary. A `BEFORE INSERT OR UPDATE` trigger now permits **new** Sources only as inactive `CANDIDATE` without reserved review/approval/activation provenance. This preserves Discovery → promotion → inactive Source registration and does not rewrite the five existing inactive `HOLD` rows. The Supabase Source repository uses INSERT for new rows and UPDATE for existing rows; `upsert` would invoke the INSERT trigger even for a conflicting approved Source. Existing Source lifecycle, type, review provenance, and approved configuration/identity changes remain guarded. A direct `service_role` UPDATE cannot pass by setting the transition GUC: the trigger also requires the execution role to be the `agent_review_source` function owner. SQL table constraints additionally reject ACTIVE rows without the approval snapshot.

`agent_source_review_events` grants `service_role` SELECT only; direct INSERT, UPDATE and DELETE are unavailable. Its UPDATE/DELETE trigger also rejects mutation by the function owner. Only the `SECURITY DEFINER` review RPC writes audit rows, in the same PostgreSQL statement/transaction as the Source transition; an audit insert failure rolls back the Source change. The RPC has a fixed `pg_catalog` search path, uses schema-qualified tables, contains no dynamic SQL, and grants EXECUTE only to `service_role` (not `PUBLIC`, `anon` or `authenticated`). It locks the Source, checks expected state and allowed transitions, requires nonblank reviewer/reason and explicit approval decisions, binds the approval snapshot to URL/domain/type/trust/confidence/collection settings, and rechecks that snapshot before activation.

This guards accidental or malformed direct application writes, including a service-role REST call. It does **not** authenticate the human named in `p_reviewer`: anyone holding the service-role credential can invoke the legitimate RPC and assert a reviewer string. Protect that credential and supply an authenticated operator identity at the calling boundary. A database owner/superuser can alter functions, grants or triggers and is outside this boundary. Do not expose the service-role credential to a client. The ACTIVE snapshot CHECK was added `NOT VALID` so historical rows were not scanned; PostgreSQL enforces it on new and updated rows. Live role-specific REST tests confirmed direct lifecycle INSERT/UPDATE and audit INSERT/UPDATE/DELETE are rejected.

## Final runtime validation (2026-10-04)

One synthetic Agent Source, `runtime_source_approval_smoke_test` (`87c7eb04-095a-4cbe-855b-ca7e3e81e439`), was registered through `SourceRegistryService` as inactive `CANDIDATE` without approval metadata. Service-role REST calls rejected direct ACTIVE and APPROVED INSERTs, preseeded approval metadata, CANDIDATE→ACTIVE/APPROVED UPDATEs, and direct audit INSERT/UPDATE/DELETE (`P0001` for lifecycle guard, `42501` for audit grants). The official `SourceApprovalService` RPC produced `CANDIDATE→REVIEW→APPROVED→ACTIVE→DISABLED` with four read-back audit events, nonblank reviewer/reason and timestamps. A temporary approval-snapshot/config mismatch was introduced **inside a PostgreSQL transaction**, activation was required to fail with `matching human approval required`, and the entire transaction was rolled back; subsequent readback showed the original APPROVED snapshot/config and two events before normal activation. No external collection request was made. CollectionRunner blocked the live APPROVED Source and passed the live ACTIVE Source to a fake Planner that stopped before HTTP; CANDIDATE/REVIEW were replayed in memory through the same Runner. Read-only Service Source mapping scanned 29 rows and found no matching `example.org` Service Source; Service writes were zero. The test Source remains DISABLED with its audit trail; the original five remain unchanged. All 145 tests passed. This synthetic decision is a security test, **not** a human-approved production Source.

`SourceRegistryService.activate()` and `deactivate()` always refuse. `register-source --activate` is explicitly refused **before registration**, so it cannot create a Source as a side effect. Generic Source repositories refuse status/type/review-provenance changes; migration 004 adds a DB lifecycle guard and an ACTIVE approval CHECK. CollectionRunner additionally refuses anything without a matching reviewed ACTIVE approval, including legacy ACTIVE rows without that record. Existing rows are not backfilled. Ordinary configuration and identity changes are frozen while APPROVED/ACTIVE; return to human review for changes. There is no approval CLI or admin UI in this phase; the Python service API is for a trusted operator application.

## Service Source identity (read-only preparation)

`approved_source_identity()` prepares Agent Source UUID, canonical URL, normalized domain and normalized name only from approved/active records. `preview_approved_source_mapping()` accepts a read-only snapshot of existing active Service Sources and requires a unique exact homepage URL, or a unique domain+name match. Optional explicit Service Source ID must still match those identity rules. Missing/ambiguous matches return a REVIEW reason; there is **no automatic Service Source creation** and no Service DB write. This preview does not itself approve Source collection or relax PHASE 7's Publish Gate; production mapping still rechecks at publish time.
